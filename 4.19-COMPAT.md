# Linux 4.19 compat

This branch carries the minimal compat changes needed to build
`hma_uidfake.ko` against an arm64 **Linux 4.19** kernel (developed and
verified on a MediaTek MT8797 Android kernel, clang r383902, out-of-tree
`make M=... modules`).

Base: upstream `dcc8c1993f35` ("docs: changelog for 0.3.3").

## Changes

### src/patch.c
- `pud_leaf()` / `pmd_leaf()` only exist from kernel 5.10 (generic pgtable
  helpers). On arm64 4.19 the equivalent block/section entry tests are
  `pud_sect()` / `pmd_sect()`, so shim macros are added for
  `LINUX_VERSION_CODE < KERNEL_VERSION(5, 10, 0)`.
- added `#include <linux/version.h>`.

## Status

`hma_uidfake.ko` compiles and links on 4.19, and every undefined import
(including `register_kprobe` / `unregister_kprobe`) resolves against the
target kernel's `Module.symvers`.

Two kernel-side facts shaped the deployment story:

- The three symbols this module calls directly — `get_task_cred`,
  `find_user`, `free_uid` — exist in 4.19 but are not exported by the stock
  kernel, which used to make `insmod` fail with "Unknown symbol in module".
  The resolution is kernel-side: the target kernel tree now carries
  `EXPORT_SYMBOL(get_task_cred)` (kernel/cred.c) and
  `EXPORT_SYMBOL(find_user)` / `EXPORT_SYMBOL(free_uid)` (kernel/user.c),
  so this module's source stays unchanged.
- The runtime resolver registers a `register_kprobe()` to locate
  `kallsyms_lookup_name`. With `CONFIG_KPROBES=n`, 4.19's
  `include/linux/kprobes.h` turns that call into an inline `-ENOSYS` stub:
  the module still compiles with zero warnings but every resolved symbol
  would silently be `NULL`.

Kernel-side requirements (outside this module's control — they live on the
target kernel tree, not here):
- the three `EXPORT_SYMBOL`s above,
- `CONFIG_KPROBES=y` for the runtime resolver, and
- the `.ko` must be paired with the kernel build it was produced against
  (vermagic and symbol CRCs must match).
